# 开发规范

本文件约定本项目的技术、目录、命名、代码与协作规范。所有贡献者与 AI 助手都应遵守。

## 1. 技术栈与边界

- 原生 HTML5 + CSS3 + JavaScript（ES Modules），不引入任何框架、构建工具或第三方运行时依赖。
- 目标浏览器：最近两个大版本的 Chrome / Edge / Safari / Firefox。
- 部署：GitHub Pages（HTTPS）。ES Modules 在同一域名下由浏览器原生加载，无需打包。
- 本地开发：通过 HTTP 服务预览（`python -m http.server` 或 VS Code Live Server）。禁止依赖 `file://` 双击打开，因为浏览器会阻止 ES Modules。
- 离线/现场使用：页面本身不请求外部资源；字体、图标一律使用系统字体与内联 SVG/CSS 绘制。

## 2. 目录与文件命名

- HTML 入口固定在根目录 `index.html`。
- 样式放 `css/`；脚本放 `js/`；纯规则数据放 `js/data/`；领域逻辑放 `js/modules/`；DOM 绑定/渲染控制器未来放 `js/ui/`。
- 静态资源（棋盘图片等）放 `assets/`。
- 文件命名：`kebab-case`（如 `rules-data.js`、`style.css`）。
- 文档名：中文文档可用中文名（如 `开发规范.md`）；跨工具敏感文件用大写英文（`README.md`、`AI_CONTEXT.md`）。

## 3. 命名规范

- 变量/函数：`camelCase`（`rollDice`、`splitBatches`）。
- 常量：`UPPER_SNAKE_CASE`（`MAX_DICE`、`BATCH_SIZE`）。
- DOM id / class：`kebab-case`（`d12-summary`、`is-active`）。
- 模块文件内尽量 `export` 纯函数，避免模块顶层副作用（`main.js` 除外）。
- 数据 key 使用英文语义键（`unit`、`stance`、`air`、`surface`），展示文案单独放中文标签映射，不要混在逻辑里。

## 4. 模块职责

- `js/data/`：只放静态规则数据，不写逻辑、不操作 DOM。
- `js/modules/`：领域逻辑（掷骰、伤害分配、压力计算等），纯函数优先，可注入随机源方便测试。
- `js/ui/`（未来）：DOM 渲染、事件监听、把领域结果映射到界面。
- `js/main.js`：组合根，负责装配模块、标签页切换等壳层行为。

## 5. 数据与规则

- 战斗值、色面分布等唯一数据源是 `js/data/rules-data.js`，并逐条标注对应 `warroom_rules.txt` 的章节。
- `warroom_rules.txt` 是精简参考，不是完整规则书；实现前如有歧义，以实体规则书/棋盘为准并记录在 `progress.md`。
- 颜色不能只靠色块表达：白/黑/红/绿/蓝/黄必须同时显示中文标签，保证可读性与色觉无障碍。

## 6. 代码与注释

- 注释使用中文，解释“为什么”与“对应哪条规则”，而不是复述代码。
- 规则引用格式示例：`// 规则 §8：每阶段最多 30 骰，超出忽略。`
- 一个函数只做一件事；超过 60 行应拆分。
- 状态变更集中管理，避免散落的全局可变状态；先用每个模块的内存状态对象，未来再考虑 `localStorage` 持久化。

## 7. Git 协作

- 主分支：`main`，保护分支；功能开发用 `feat/xxx` 分支。
- Commit 使用 Conventional Commits：`feat:`、`fix:`、`docs:`、`refactor:`、`chore:`。
- 每次提交同步更新 `task.md`（勾选/新增任务）与 `progress.md`（记录变更与下一步）。
- 提交前本地自测：核心模块用注入固定随机源的确定性样例自检。

## 8. 验收与测试

- 现阶段不引入测试框架，采用“确定性样例 + 浏览器手测清单”：
  1. 掷骰数量校验（0、正数、30 上限、超限报错）。
  2. 每批最多 10 骰，只有最后一批可不足 10。
  3. 颜色归组统计与 D12 面数分布一致（用固定随机源验证）。
- UI 手测：标签页切换、规则速查表渲染、移动端窄屏可读。

## 9. 变更流程

1. 在 `task.md` 创建/更新任务。
2. 实现并同步 `progress.md`。
3. 自测通过后提交。
4. 若规则数据与棋盘图片冲突，先记录差异再修改，避免静默覆盖。
